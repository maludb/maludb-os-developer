# Build spec: the estate, access and the object browser (slice 1 — the CRUD exemplar)

What exists at the end: every database the cluster has is **discovered** by the worker through the door and appears in **the registry**
with a proposed class (the fixed precedence of design §6.2, `dx_propose_class()`); a super-admin **confirms** each — class, application,
private flag, label, colour, hidden — and, while its grants are pending, reads **the root step the owner runs once**
(`sudo deploy/grant-target.sh subello_boards application`) until the worker sees them `in_place`; a super-admin grants **access levels**
(masked or rows) per database to a person (the record picker) or a role; the **classifier** proposes `secret` and `personal` columns on
every catalog pass and **the grants service** keeps the tiers' column privileges in step within a minute — masks as privileges, enforced at
once; a DBA confirms or clears a proposal. Every person sees **the databases their class shows them as cards** by class, opens one (its
overview — version, size by schema, extensions against their defaults, non-default settings — and its verb tabs), walks schema → family →
object through **paged, filtered tables that ask the catalog one node at a time** (a schema of 10,000 tables stays usable), **searches
names, columns, types and comments across every database they may see** (the catalog index, by trigram), keeps **favourites** and
**recents**, and lands on **the object page's skeleton**: its header, its tabs (slice 2 fills them), a table's columns, and the definition
from `pg_get_*def` where PostgreSQL has one. **This slice is Developer's CRUD exemplar**: every later record screen copies its files, its
pages' shape, its handler's order (`dx_handler_begin()` → `require_human()` where the row says `people` → `require_right()` → the target
gate (`dx_target_or_404()`) → `dx_guard()` around the database's own statement or function, or the door's client → `log_activity()` →
`dx_done()`) and its proof. It replicates the estate's CRUD exemplars — read `/srv/apps/boards/docs/build-specs/boards-folders.md`, the Data
Lake's `catalog.md` and their built files first.

Schema (db/006–008, 012, never modified): `target_databases`, `dx_propose_class()`, `target_access` + `dx_target_access_before`,
`dx_person_level()`, `favourites`, `recents`, `dx_door_policy()` (db/006); `catalog_index`, `catalog_index_passes` (db/007);
`column_classes`, `dx_classify_column()`, `dx_classify_propose()`, `dx_classify_confirm()`, `mcp_grant_plan`, `mcp_grant_targets`,
`grants_passes`, `dx_grants_pass_log()` (db/008); `dx_caller_may()`, `dx_address()`, `mcp_visible_targets`, `mcp_target_databases`,
`mcp_catalog_index`, `mcp_registry_changes`, `mcp_access_levels`, `mcp_column_classes` (db/012). **The database is the referee**: the name
pattern, the class checks (a workbench is `dxw_<n>`, private only for an application, an application names its key), a level never an
agent's, `rows` only for a holder of `data.unmask`, no level on the kernel's or a memory database, a pattern-matched secret cleared only by a
super-admin, the classifier never overwriting a person's call.

## Divergences from the design
1. **The registry's writes are plain statements, not database functions.** `target_databases` carries every rule as a CHECK; the handlers
   (`app/features/estate/write.php`) run `UPDATE target_databases SET … WHERE datname = :d` under `registry.manage` inside `dx_guard()`.
   Confirming a class sets `confirmed_by`/`confirmed_at`; confirming `application` or `development` sets `grants_state = 'pending'` until the
   worker's next probe; confirming `unclassified` undoes a confirmation (the database is no longer reached).
2. **Favourites are keyed by the object, not by an id** (`favourites`' primary key is member × target × the address parts). `favourite_remove`
   takes `target` and `object` like `favourite_add` — the manifest's `**favourite**` param is the same pair (a defect reported to the planning
   model; until the manifest changes, the handler also accepts `favourite` as `<datname>|<address>`). record_id is the address.
3. **The object page is a skeleton here.** Slice 1 builds the header, the tab strip (each tab a link to slice 2's page — its placeholder until
   then), the Columns tab of a relation and the **Definition** section for the families PostgreSQL rebuilds itself (`pg_get_viewdef`,
   `pg_get_functiondef`, `pg_get_indexdef`, `pg_get_constraintdef`, `pg_get_triggerdef`, `pg_get_ruledef`, `pg_get_statisticsobjdef`) — every
   other family says "DDL is generated by slice 2". The danger zone shows its three buttons disabled with "Built by slice 4".
4. **The application keys the precedence needs** come from the kernel's switcher feed (K31, `GET /api/v1/apps/mine.php`) read by the worker as
   the first active super-admin of the mirror, cached for an hour in the worker's memory — never written to a table.

## Discovery, the catalog index and the grants (the worker and the services)
- **Discovery** (every pass, a minute): the door's named `databases` (as `developer_meta`, the worker as its source) lists `pg_database`; a
  name outside `^[a-z0-9_]{1,63}$` is skipped and logged once; a new database is inserted `unclassified` with `proposed_class` and
  `proposal_reason` from `dx_propose_class(datname, has_maludb, app_keys, tenant)` after one named probe `database_probe` (its extensions,
  memory schemas, size, version) — logged `registry.appeared` (source `cron`); one no longer listed gets `gone_at` (`registry.gone`), never a
  delete. For every confirmed application or development target the named `grants_state` reads, per table, whether the tool's tiers hold
  their privileges (`has_table_privilege()` / `has_column_privilege()` by `developer_meta`) and sets `grants_state` (`pending` → `in_place` /
  `partial` / `revoked`), logging `grants.change` when it moves.
- **The catalog index** (each target at most every 10 minutes, oldest first, `catalog_index_pass` limited per pass; on demand by
  `catalog_refresh`): the named `catalog_dump` pages through every object of the target — address parts, family, schema, name, owner, comment,
  extension, `is_system`, and a relation's columns with types — and replaces that target's rows in one transaction, writing a
  `catalog_index_passes` row. For every column it calls `dx_classify_propose()` (the deterministic classifier, in SQL). Memory databases are
  indexed for their state only (the memory section); the kernel's database is indexed (structure only). A system schema's objects carry
  `is_system` and are left out of search unless asked.
- **The grants service** (`developer-grants`, every minute, its own user and passfile — never the door): reads `mcp_grant_plan` as
  `developer_grantor`, grants and revokes the tiers' column privileges per target (secret → no tier; personal → `read` and `write` only; else
  all three; `xmin` granted with the readable columns; a column matching the built-in secret patterns never granted unless a super-admin
  cleared it), and records each pass with `dx_grants_pass_log()`. **A proposal is enforced at once**: the next pass revokes the column, so
  a `masked` reader's `SELECT email …` is refused by PostgreSQL within a minute of the classifier's proposal.

## Decisions taken here
1. The registry's writes are plain statements under `registry.manage`; the CHECKs are the rules (divergence 1).
2. A favourite is keyed by target and address; `favourite_remove` takes the same pair (divergence 2, reported).
3. The application keys come from the kernel's switcher feed read by the worker as a super-admin, never stored.
4. The catalog index replaces a target's rows whole each pass (one transaction) — simpler than a diff, and the index is a cache.
5. Search leaves system schemas out unless `family` or a "system objects" switch asks for them.
6. The family page's count is the catalog's estimate for relations and an exact count only below 10,000 objects; above, "10,000+".
